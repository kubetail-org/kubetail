# src/components/dashboard — the dashboard

The resource nav, the pages, the objects and events tables, the object panel and `VirtualTable`. Also owns `src/lib/`'s `dashboard-resources.ts`, `cluster-cached-data-*.tsx`, `cluster-namespaces.tsx`, `object-*.ts[x]`, `table-columns.ts`, `sort-rows.ts` and `jsonpath.ts`. The webview-wide rules, security invariants first, are [`src/CLAUDE.md`](../../CLAUDE.md), which also has how the window bounds a table's scroll (*Window state*).

## The resource nav

`DashboardResourceNav` (`components/dashboard/dashboard-resource-nav/`, exporting the nav alone) draws the pinned Overview and Events rows (`NavItem`), a rule, a sticky search box, then a *Namespace* and a *Cluster* section (`SectionHeading`, in `primitives/`, with its layers or globe icon) of groups (`NavGroup`) of kinds. `buildDashboardNav(kinds)` (`src/lib/dashboard-resources.ts`) places each kind: **its scope is its section**; its group is the curated kind's (`GROUPS`), else its API group's (`API_GROUP_TO_GROUP`), else a core plural's (`CORE_KIND_TO_GROUP`), else *Custom resources* for a CRD and *Extensions* for the rest. A curated kind matches on API group **and** plural, so a CRD reusing a built-in's plural never takes its row. A curated or core kind's id is its plural, any other's `<group>/<resource>`; Events are the pinned row, never a section's kind. **Before the catalog's `Bookmark` (`useDashboardNav` gates on it) the tree is the curated kinds without counts and nothing hides.** After it, `filterNav` hides kinds with no objects, the current kind excepted; a search reaches them; a search is a case-insensitive prefix match on kind labels that holds every group open. Group rows only open and close; a closed group holding the current kind draws as selected (`SELECTED`, shared with `NavItem`). Each group's open state is a `usePersistedFlag` (`dashboard-nav-open:<section>/<group>`); with nothing stored, each section's first group starts open and the rest closed; moving to a kind opens its group. A section heading is a label, not a toggle; the breadcrumb bar's picker names the namespace scope, so the *Namespace* heading does not. Kind labels draw through `VisibleText`. `DashboardResource` is an **open string**, validated leniently. → [ADR: dashboard nav merge](../../../docs/adr/2026-08-09-dashboard-nav-merge.md), [ADR: the dashboard nav groups kinds by scope and API group](../../../docs/adr/2026-11-12-the-dashboard-nav-groups-kinds-by-scope-and-api-group.md).

## Live data

`ClusterCachedDataKindsProvider` (`src/lib/cluster-cached-data-kinds.tsx`) holds the window's **one** `clusterCachedDataKindCollectionWatch(id, cacheID, namespace)` subscription, **subscribed with the namespace scope**: each namespaced kind's count (and Events') is the namespace's, a cluster-scoped kind's the whole cache's. The frame's echoed `namespace` joins `cacheID` in its provenance, so a namespace switch re-subscribes like a cache swap. `AppLayout` mounts it above the sidebar and the routes, enabled only on the dashboard, so the catalog outlives the nav's card and a reopened nav reads it whole. `useClusterCachedDataKinds` reads it; `useDashboardNav` builds the tree over it.

All three cached-data hooks resolve the cluster/cache through `useActiveCluster()` (`src/lib/active-cluster.tsx`) and reduce through **`useCacheCollectionWatch`** (`src/lib/graphql/use-cache-collection-watch.ts`), which owns the id-keyed fold, `subscriptionPhase`, and the **cache/kind provenance guard** (rejects rows from a superseded cache — don't bypass it; → [`docs/data-access.md`](../../../docs/data-access.md)). `AppLayout` mounts `DashboardResourceNav` only while `/dashboard` matches, and `ClusterNamespacesProvider` (`src/lib/cluster-namespaces.tsx`) beside the catalog's provider, enabled the same way: the window's one `v1/namespaces` watch, `unshared`, since a Namespaces page watches the same kind and the later of two shared consumers never sees the snapshot.

**The namespace picker** is the breadcrumb bar's right end: a `ScopeMenu` behind a `ScopeTrigger` chip (`breadcrumb-bar/scope-menu.tsx`), a combobox search box over a listbox of options under labels; the caller's `entries(query)` decides what matches; the arrows move the highlight over options from the box, Enter picks, and it opens scrolled to the current option. Its menu is *All namespaces*, then the namespaces matching a substring, the chosen one kept (*Not found* once the list has landed without it). Under a search, Enter never takes *All namespaces* (`explicit`) unless it is highlighted.

## Pages

**A dashboard page is `DashboardBreadcrumbBar`** (`components/dashboard/breadcrumb-bar/`) **over a note (`PageHeader`) and its panel**, with no toolbar. The bar names the page by `useDashboardNavPlace`, which places the one kind without building the tree, the page's held kind through a replay: Overview and Events by their nav icons, a kind as its section's icon, its group and its label; the nav and the bar share the icons (`src/lib/dashboard-nav.tsx`), and the bar names a kind's section to a screen reader. `routes/dashboard.tsx` picks a page from `resource`: `events` → `EventsPage` (`useClusterCachedDataEvents`, then `EventsTable`); a resolved discovered kind → `KindPage` (`useClusterCachedDataObjects(kind)`, keyed by cache **plus** `apiVersion`+`resource`, then `ObjectsTable`), held through a reconnect's replay of the catalog so the table stays mounted. **A page owns its watch and filters it by the namespace scope**; a cluster-scoped kind is not filtered and says so under a namespace. Anything else is `PlaceholderPage`: a resource `mayNameDiscoveredKind` accepts (anything but Overview) but the catalog lacks reads "not synced" with no active cache, a spinner before the Bookmark, and "not served" after it; Overview reads "coming soon". The label is `dashboardResourceLabel`'s. `rawJSON` is the full native body (`unknown`). Both tables take their rows, `active` and `phase` as props and gate on them: no active cache → "not synced", `connecting` → spinner, `live` with no rows → "No …" (naming the namespace under a scope, where `ObjectsTable` also drops its Namespace column).

## Columns

**A kind's columns come from `components/dashboard/objects-table/columns/`**, which exports `columnsForKind`, `toneForKind`, `Age` and `ageSortValue`:

- **A hand-written entry wins**, else the kind's `printerColumns` evaluated by `src/lib/jsonpath.ts`. Those kubectl prints only under `-o wide` (`priority > 0`) are `hiddenByDefault`. A printer column's value truncates to its column, like a built-in text column's. Its key is its name (`printer:<name>`), not its place, so a user's choices for it hold when the CRD adds or moves another.
- **Every built-in kind is hand-written**, one file per nav group (`pods.tsx`, `workloads.tsx`, `cluster.tsx`, `dra.tsx` for dynamic resource allocation, `network.tsx`, `config.tsx`, `storage.tsx`, `access.tsx`, `extensions.tsx`); `registry.tsx` joins them by `gvrKey`. Each draws kubectl's columns; its `-o wide` columns and more of the object's fields are `hiddenByDefault`.
- **A kind's entry is `kind<Body>(apiVersion, resource, columns)`** (`common.tsx`). `Body` is the narrow shape the kind reads off `rawJSON`, named once. Each column is a builder (`textColumn`, `listColumn`, `countColumn`, `quantityColumn`, `readyColumn`, `ageColumn`, `durationColumn`, `statusColumn`) over a reader of that body, or a `KindColumn` written out where none fits.
- **A status column gives the kind its tone.** `statusColumn`'s reader returns the label and tone of its `StatusPill` (`components/dashboard/status-pill.tsx`), and `toneForKind` reads the tone off that column, so the tabs and the pill cannot disagree. The pill carries its whole label as its `title`. A PersistentVolume or claim being deleted reads *Terminating*, whatever its phase. A tone is drawn in cluster health's palette: `HEALTH_TONE` maps it onto `TONE` (green, amber, red). A Deployment's status is `kubectl rollout status`'s reading. Until the current generation is observed it is *Progressing*, whatever an earlier rollout's conditions say. It is *Available* once every desired replica is updated, no old one is left, and every updated one is available.
- **A cell is redrawn only on a new frame**, so one that reads the clock ticks itself: `Age` through `react-timeago`, a running Job's Duration through `Elapsed` (`primitives/elapsed.tsx`), which stops once the Job has a `completionTime`. A column whose sort value reads the clock says so (`sortsByClock`), and the table sorts by it again each second.
- **A pod's tone is its status's (`podStatusTone`), except that a running pod is `pending` until its Ready condition holds**, so a starting pod never reads failing and a never-ready one never reads healthy. Its columns are Status, Ready, Restarts (destructive above zero) and Node.

## The objects table

**`ObjectsTable` draws a kind's rows in a card on the page's background** (`components/dashboard/objects-table/`, exporting the table alone): a muted header row, cells tighter than the library's (12px between columns), and a *Showing N of M* footer.

- **Rows are two lines tall** (`TALL_ROW`), their cells without vertical padding: a row's height is only a minimum, and two lines under the library's padding would outgrow the height the table's arithmetic assumes. Name is the name over its owning workload (`ownerOf`, `src/lib/object-owner.ts`: the controller owner, a Deployment's ReplicaSet read as the Deployment by its `pod-template-hash`). Age is as kubectl prints it (*22m*, *3d*).
- **A kind with a tone gets status tabs above the table**: *All · Healthy · Failing · Pending*, with counts over the scope's rows, each count above zero in its tone's colour. A tab filters the rows, and the footer counts what it shows. A tab or a filter that leaves no row draws the table empty (*Showing 0 of N*).
- **A text filter sits under the tabs, just over the table**: a `SearchBox` that Escape clears. `matchesFilter` (`src/lib/object-filter.ts`) matches a case-insensitive substring of the name, the owner as drawn, a label as `key=value`, the node, or the namespace while its column shows. A custom resource can hold anything at `spec.nodeName`, so only a string there is matched. It narrows the rows before the tabs count them.
- **A column picker sits at the filter's right** (`ColumnPicker`, `objects-table/column-picker.tsx`): every column in the table's order, each with a checkbox, Name's locked on, and a handle that drags it to another place or moves it from the keyboard. *Reset* returns to the defaults. The popup is no taller than the room it has, and its list scrolls. The handle goes through dnd-kit's pointer and keyboard sensors, never HTML drag and drop, which Tauri's file drop swallows on Windows.
- **`useTableColumns` (`src/lib/table-columns.ts`) keeps the user's choices and order per kind in localStorage**, each against the column's default, so a column the table gains later takes its own default place and visibility (`arrange`). A `hiddenByDefault` column waits to be picked, as Pods' IP, Host IP, Containers, Images, QoS class, Service account, Priority class, Controlled by and Started do.
- **A column with a `sortValue` sorts.** Its header is a button with two muted triangles, the sorted direction lit. The first press sorts it (largest first for a `descFirst` count), the next reverses it, the next returns to the watch's order. `sortRows` (`src/lib/sort-rows.ts`) is stable and puts a missing value last. The sort is the table's own state, reset by keying the table on its kind, and the footer names it (*Sorted by restarts*).
- **The last column is the row's actions** (`actionsColumn`, `objects-table/actions.tsx`): a ⋯ button on every row, then a › that opens the object on its YAML, under no header, outside the column picker and its order, and `pinned` to the right edge so a narrow page's sideways scroll never hides it. Its menu is *View YAML* and *View events* for every kind, and *View logs* for the kinds of `LogsViewSourceKind` (`logsSourceKind`, `src/lib/object-actions.ts`, maps a `gvrKey` onto one, so a CRD reusing a built-in's kind name is not one; the object panel's Logs tab reads it too). Each item goes to the table's `onAction` with the row, which `KindPage` (`routes/dashboard.tsx`) answers by focusing the object on that tab.

## The object panel

**The focused object is `useObjectView`** (`src/lib/object-view.tsx`): the object's kind, `uid`, namespace and name, or null, and its open tab (`yaml`, `events` or `logs`). It is chrome, like the focused log view: out of the URL, so Back and Forward leave it alone, and not persisted. `set` opens the right sidebar. The object is bound to the cluster it was focused in: `ObjectViewProvider` drops it once the active cluster is another, however the window got there (the picker, Back, a new default context). `ObjectPanel` (`components/dashboard/object-panel/`, exporting the panel alone; `object-panel/panel.tsx`, keyed on the uid) draws a header naming the object, with Close, over its tabs, mounting the open tab alone. Close clears the object and the chat comes back.

- **YAML** (`object-panel/yaml-view.tsx`): `objectYaml` (`src/lib/object-yaml.ts`, the `yaml` package) prints the body kubectl's way, drawn through `HighlightedText`, with Copy. The last body seen is held through a reconnect and, once the object is gone after a `Bookmark`, marked *Deleted*.
- **Events** (`object-panel/events-view.tsx`): the cache's Kubernetes Events whose involved kind, namespace and name are the object's, newest first. Each draws its type (`TypeBadge`, from `events-table.tsx`), reason, count, age and wrapped message, through `VisibleText`.
- **Logs** (`object-panel/logs-view.tsx`), for a log kind alone: `LogViewer` over a `LogsViewAction` the tab builds, with no chat behind it. The object is its one source (a workload reads its pods), every container, landing at the tail and pinned. The grep the toolbar applies lasts the mount, and its viewport handle goes unread: the dashboard chat sends no snapshot.
- **YAML and Events each hold an `unshared` watch of their own**, so they stay live whatever page the window shows. A second shared consumer of a running watch would never see its snapshot.

## The virtual table

**Both tables render through `VirtualTable`** (`components/dashboard/virtual-table.tsx`), only the on-screen rows in the DOM between two spacer rows. These hold it up:

- **Every row of a table is one height, `ROW_H` unless the table passes a `rowSize` (`TALL_ROW`), and the pixels are read off a rendered row** (`TableRow`'s `border-b` under collapsed borders makes it not `h-9` arithmetic). A wrong constant drifts rows further down a long list.
- **The table is `table-fixed`**: widths come from a `<colgroup>` the header's table and the body's share (the body's first row is a spacer with no cells), each column's `width` in pixels (`columns/` sizes every kind column); free-text columns `truncate` with a `title`. The one unsized column (Name, an event's Message) takes the slack and keeps its `minWidth`: the table's minimum width is the sum, so a narrow page scrolls sideways rather than squeezing that column to nothing. `ObjectColumn` is a `VirtualColumn` whose `width` is required.
- **The header is a table of its own above the scroller**, so the scrollbar starts under it. It pads its right edge by the scroller's bar (`offsetWidth − clientWidth`), so its columns stay over the rows'. It follows the scroller's `scrollLeft` by a `translateX`, never by scrolling itself: WebKit leaves that padding out of a box's scroll range, so a scrolled header would stop short at the far right. A header button taking focus scrolls the rows by the least that shows it beside the pinned ones. **Pinned columns come last, with no header text and no sort**: their header cells sit under one patch, and each body cell sticks at the width of the pinned columns after it.
- **The two tables read as one.** The wrapper is `role="table"`, both native tables are `role="none"`, and their sections, rows, headers and cells name their own roles, so a screen reader ties each cell to its column's header.
- **The scroller's bar is `table-scrollbar`** (`index.css`). Styling WebKit's bar makes it a classic one beside the rows, so their borders never show through a macOS overlay bar. It sets only the `-webkit-` pseudo-elements: Chromium drops them once `scrollbar-width` or `scrollbar-color` is set.

**The table corrects its own scroll**: after each commit it moves `scrollTop` by the *smallest* shift any surviving on-screen row made, doing nothing within one row of the top; the scroller sets `overflow-anchor: none`. The window is clamped to the rows there are, so a list a filter or a tab cuts short under a deep scroll still draws its rows. → [ADR: the virtual table owns its scroll anchoring](../../../docs/adr/2026-10-17-the-virtual-table-owns-its-scroll-anchoring.md). The scroller is `tabIndex={0}` for Home/End/PageUp/PageDown.
