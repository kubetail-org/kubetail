# Attest build provenance in the release jobs

## Context

In November 2026 the release workflow audit (#1282) found that nothing tied a release to the run and commit that built it. The CLI's assets carried `SHA256SUMS.asc` and platform code signatures, but no provenance. The images carried the provenance BuildKit attaches by default. That provenance is written inside `build-and-publish` by the same tooling that runs the Dockerfile, and is signed only indirectly, by `cosign sign -r` over the index.

SLSA Build L1 asks for provenance. L2 asks that the hosted build platform sign it. L3 asks that the build's own steps cannot forge it: the signing identity must be out of their reach.

GitHub's `actions/attest` writes a SLSA provenance statement, signs it with a short-lived Sigstore certificate issued for the job's OIDC identity, and stores it in the repository's attestations, where `gh attestation verify` finds it by digest.

## Decision

Both release workflows attest what they publish with `actions/attest`:

- The `release` job of `release-cli.yml` attests every file in `assets/`, the checksums included, before it creates the draft release.
- The `create-and-publish-manifest` job of `release-docker.yml` attests the index digest it pushed, once per registry, with `push-to-registry: true`, before it moves `latest`.

Only these jobs hold `id-token: write` and `attestations: write`. A dry run attests nothing. `SECURITY.md` gives the `gh attestation verify` commands, pinned to the release tag and the signing workflow.

This reaches SLSA Build L2. We stop short of L3.

## Alternatives considered

**Reach L3 with a reusable workflow that builds and attests.** The certificate then names the reusable workflow, which a verifier pins with `--signer-workflow`, so a step in the calling workflow cannot produce an attestation that passes. The build has to move with it, or the reusable workflow attests whatever digest its caller hands it. The CLI build spans the `prepare`, `build`, `sign-darwin`, `sign-windows`, `verify-signatures` and `package-tarball` jobs, with SignPath, Apple notarization and the `production` environment's secrets; the image build is a matrix of four. Moving both into reusable workflows restructures each release for a gain over L2 that covers only a compromised step inside our own release workflows, where every action is pinned to a commit SHA and `id-token: write` is already confined to the attesting jobs.

**Keep BuildKit's default provenance for the images.** It is generated by the build it describes, so a compromised build step can write what it likes into it. It also covers each platform image alone, not the index users pull.

**Attest each platform digest of an image as well as the index.** `gh attestation verify oci://…:<tag>` resolves the tag to the index, and `cosign sign -r` already signs the platform images. A further four attestations per variant would add nothing a verifier asks for.

## Consequences

A user can tie a CLI download or an image to the tag, commit and workflow run that built it, with `gh attestation verify` and no key of ours.

The verify commands in `SECURITY.md` name `release-cli.yml`, `release-docker.yml` and the tag scheme. Renaming a workflow file, or moving the attest step into another workflow, changes the signer identity and breaks those commands for every release from then on.

The attestation records the ref the workflow ran from. A release published by a `workflow_dispatch` records the dispatching branch, not the tag, so `--source-ref refs/tags/…` rejects it. A release for users is published by its tag push.

## Revisit when

A distributor or user requires SLSA Build L3, or the release workflows are restructured for another reason.
