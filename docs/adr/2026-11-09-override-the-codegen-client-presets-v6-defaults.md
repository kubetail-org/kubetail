# Override the codegen client preset's v6 defaults

## Context

The UI's GraphQL types are generated by `@graphql-codegen/client-preset` (`dashboard-ui/codegen.ts`). In June 2026, #1166 (`185c2f93`) upgraded it from v5 to v6, with `@graphql-codegen/cli` v7 and Apollo Client 4, to keep the frontend on current, supported versions.

The commit body records that client-preset v6 changed three defaults. Custom scalars became `unknown` where they had been `any`. GraphQL enums became string-union types where they had been native TypeScript enums. `__typename` was no longer added to operation and fragment types. The PR's stated aim was that "the generated types keep the shapes the app and Apollo cache expect".

The app depends on each of the old shapes. It reads custom scalars as `any` and converts them in the cache's `dateField` and `bigIntField` read functions (`src/apollo-client.ts`). It uses enum members as values: `HealthCheckStatus.Success` in `lib/server-status.ts`, `LogRecordsQueryMode.Head` and `.Tail` in `pages/console/download.tsx` and `log-server-client.ts`, `WatchEventType.Added` in tests. And Apollo Client adds `__typename` to the documents it sends, so every object the app receives carries one.

The comment above the config in `codegen.ts` records why the root is treated apart. Apollo never requests `__typename` on the operation root: its runtime `addTypename` adds it to nested fields only.

## Decision

Both `client` presets in `codegen.ts`, for the Dashboard and the Cluster API, set four options:

- `defaultScalarType: 'any'`: custom scalars are `any`.
- `enumType: 'native'`: GraphQL enums are native TypeScript enums.
- `nonOptionalTypename: true`: every object type in an operation or fragment carries a required `__typename`.
- `skipTypeNameForRoot: true`: the operation's root type carries none.

The first two restore v5's output exactly. The second two are not a restoration. v5 emitted an optional `__typename?:` on every object type and on the root. The config now matches what Apollo returns at run time instead: a typename on each nested object, none on the root.

## Alternatives considered

**Stay on client-preset v5.** Rejected by #1166, whose purpose was to move to current, supported major versions.

**Take the v6 defaults.** Not recorded as weighed in #1166; the commit chose to "pin codegen config to restore the prior shapes". It would have meant replacing every enum member in the app with a string literal, casting every custom scalar out of `unknown` before the cache's read functions or a view could use it, and losing `__typename` from types whose objects carry one at run time.

## Consequences

The generated types say what Apollo delivers: a test mock or fixture typed with a generated type must now include `__typename` on every nested object, as #1166 added across `src/mocks/` and the console tests, and must leave it off the root. The tighter types let #1166 drop several `as never` and `as <Type>` assertions.

Custom scalars stay unchecked. A new time or int64 field is `any` in its generated type, and becomes a `Date` or `bigint` only if a type policy in `apollo-client.ts` converts it. Nothing in the types flags a missing policy.

The four options are written twice, once per preset. A change to one belongs in both, or the two servers' types take different shapes.

The upgrade also changed shapes the config does not touch. In the generated operation types, v6 dropped the `?` from nullable fields, so they are `T | null` rather than optional. #1166 adjusted call sites for the new types.

## Revisit when

The app stops using enum members as values, or gives every custom scalar a concrete type through codegen's `scalars` option. Either removes a reason for one of the overrides. A client-preset major that changes these defaults again calls for the same check.
