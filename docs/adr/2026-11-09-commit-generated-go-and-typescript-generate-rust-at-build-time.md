# Commit generated Go and TypeScript, generate Rust at build time

## Context

The repo generates code from three contracts: the two GraphQL schemas, and `proto/cluster_agent.proto`. Each side settled its rule when it first appeared. gqlgen's `graph/generated.go` and the UI's `__generated__/` have been committed since the first commit (`43df48a9`, February 2024). The Go protobuf code has been committed since the Go agent and its `agentpb` package arrived in #113 (`66fde8c2`, September 2024), generated by a `//go:generate protoc` directive. The first Rust consumer of the proto, `rgkl`, generated its code in a `build.rs` from the start (#227, `475751af`, April 2025). The new Rust workspace moved that `build.rs` into `crates/types` (#497, `857fcbd2`, June 2025).

The original reasoning is not recorded in any of these commits or PRs. Each rule matches its toolchain's own convention. `go build` never runs `go generate`, so Go code that is not committed does not exist for a plain build. Cargo runs `build.rs` on every build, so Rust code generated there is always current.

## Decision

Generated Go and TypeScript are committed and never hand-edited: `modules/shared/clusteragentpb/*.pb.go` and `testpb/*.pb.go` (protoc, `go generate`), `graph/generated.go` and `graph/model/models_gen.go` in `modules/dashboard` and `modules/cluster-api` (gqlgen, `go generate`), and `dashboard-ui/src/lib/graphql/*/__generated__/` (`pnpm graphql-codegen`).

The Rust gRPC code is generated by `crates/types/build.rs` with `tonic_prost_build` into `$OUT_DIR` on every build, and is never committed.

## Alternatives considered

**Generate the Go code during the build.** Not recorded as considered. The builds do not support it. The Go Dockerfiles copy no `proto/` and install no `protoc`. The CLI's release builds with `go build -mod=vendor` from a vendored source tarball, which package managers rebuild with Go alone.

**Generate the UI's types during `pnpm build`.** Not recorded as considered. `codegen.ts` reads the schemas from `../modules/`, and the frontend stage of `Dockerfile.dashboard` copies only `dashboard-ui/`.

**Commit the Rust code.** Not recorded as considered. `tonic_prost_build` writes to `$OUT_DIR` by default, and `crates/types` re-exports it with nothing hand-written beside it.

## Consequences

A Go or UI build needs neither `protoc` nor gqlgen nor codegen, and the vendored CLI tarball builds anywhere Go does. A Rust build needs `protoc` everywhere: `Dockerfile.cluster-agent` installs `protobuf-compiler`, and only the Rust CI jobs set it up.

The two sides of the gRPC contract are kept current differently. The Rust side follows the proto on every build. The Go side is as current as its last `go generate`. A proto edit without regeneration still compiles, and leaves the Cluster API and the agent disagreeing on the wire. gqlgen binds the `LogMetadata*` messages into the Cluster API's schema, so a stale `*.pb.go` is also a stale GraphQL type.

**CI does not regenerate or diff any committed output.** A stale file is caught only by a build that fails against it or by a reviewer. #1220 lists this as an open defect. A schema change under `modules/` does not run the TypeScript jobs either.

Generated files are large in review: #1166 changed about 1,900 lines of the Dashboard's `graphql.ts`. The `*.pb.go` headers record the `protoc` and plugin versions, so regenerating with another `protoc` changes them.

## Revisit when

CI gains a job that regenerates the committed output and fails on a diff. The committed files would then be checked rather than trusted. Separately, if every Go build path came to have `protoc` and the proto, generating the Go code at build time would become possible.
